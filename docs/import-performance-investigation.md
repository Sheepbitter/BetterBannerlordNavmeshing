# Where does editor navmesh time actually go? (import-performance investigation)

Status: investigation / research (read-only). No code was changed. All engine claims are sourced from
decompiled managed assemblies (`bin\Win64_Shipping_wEditor`, Bannerlord **v1.4.8**) or from string/symbol
evidence inside `TaleWorlds.Native.dll`. Native code could **not** be decompiled here (no PDB, Ghidra not
reachable) — every native claim is marked as such.

Scope: `Scene.ImportNavigationMeshPrefab` and the surrounding editor work. The 1.07 M-face "hung forever"
import is explicitly **out of scope** (structurally invalid mesh; fix in flight elsewhere) — but its log is
used once as evidence for what the hang *is* (a native call that never returns).

Observations that matter:

- **Import is linear and cheap**: ~1.0–1.4 M faces/s, no visible fixed cost. `1,509,177` faces in **1,091 ms**.
- **`ClearNavMesh()` is cheap**: 2–46 ms for 0 → 1.5 M faces.
- **`.bin` write is I/O bound, not face-count bound**: 130 MB in 260 ms.
- **Our generation dominates wall time by 1–2 orders of magnitude**: v1 build 0.02–1.2 s; v2 build 0.8 s (cs 2.0)
  up to **61.3 s** (cs 0.1). `v2 timings: tilesMs=61130 mergeMs=59` on `NavMesh_20260926_133109.log`.
- **`importMs=0` can be a silent no-op, not a fast import.** The 1.07 M-face run ("00:33:10") logged
  `facesAfter import: 0` and `increased=False`: the prefab was written this session and the native prefab list
  had not been rebuilt, so `LoadNavMeshPrefab` returned instantly without importing. Measurement caveat:
  **always read `faces after import` alongside `importMs`.**
- **The actual hang** (`NavMesh_20260929_003945.log`) ends at
  `importing prefab 'mp_battle_na'ilu_L_navmesh' (shift 0)...` with **no** `import call returned.` — i.e. the
  never-returning frame is inside the native `LoadNavMeshPrefab` call itself, not in our mesher.
- **Detail mesh multiplies faces ≈5.8×**: same run, tiles produced `polys=184,248`, the welded/emitted mesh was
  `F=1,069,997` (~5.8×). Vertex count went `1,282,576 → 706,057` after weld. So detail is the single biggest
  mesh-size lever we already control.

## 2. Managed call chains found (source-cited)

All decompiled from `D:\...\bin\Win64_Shipping_wEditor\` (v1.4.8). Tokens are the dnSpy method tokens.

```
Scene.ImportNavigationMeshPrefab(string navMeshPrefabName, int navMeshGroupShift)   // TaleWorlds.Engine.Scene, 0x06000B9B
└─ EngineApplicationInterface.IScene.LoadNavMeshPrefab(Pointer, name, shift)
   └─ ManagedCallbacks.ScriptingInterfaceOfIScene.LoadNavMeshPrefab(...)            // TaleWorlds.Engine.AutoGenerated, 0x0600049C
      └─ call_LoadNavMeshPrefabDelegate(scenePtr, utf8Name, shift)                  // native function pointer
```

`ScriptingInterfaceOfIScene.LoadNavMeshPrefab` is the entire managed body: it UTF-8 encodes the name (into a
shared 1 KB `StringBuffer0`, or a fresh array if longer) and invokes a delegate. The delegate is a native
function pointer installed by the engine (`ManagedCallbacks` callback table). **The managed side does no work
beyond string marshalling.**

Identical thin-shim pattern (all `TaleWorlds.Engine.Scene`, all one native delegate call):

| `SaveNavMeshPrefabWithFrame(string,MatrixFrame)` | `0x06000B9D` | `SaveNavMeshPrefabWithFrame` |

`Scene.Read` (three overloads, `0x06000B73/74/75`) reads a public `SceneInitializationData` struct that
carries a `bool LoadNavMesh` field:

```csharp
public SceneInitializationData(bool initializeWithDefaults)
{
    if (initializeWithDefaults) { ... this.LoadNavMesh = true; ... }   // 0x06000ABE
    else                        { ... this.LoadNavMesh = false; ... }
}
```

`Scene.Read(string sceneName)` passes `new SceneInitializationData(true)` → **LoadNavMesh = true**.
Only two references to `LoadNavMesh` exist in the whole managed engine (both inside that constructor), so no
managed code ever toggles it — it is a caller-facing knob only.

**Managed callers (whole game), via `FindCallers`:**

- `Scene.ImportNavigationMeshPrefab` — only **2** callers:
  `MissionObject.AttachDynamicNavmeshToEntity` (`0x06002225`) and `SiegeTower.AttachDynamicNavmeshToEntity`
  (both in `TaleWorlds.MountAndBlade`, used for in-game dynamic siege navmesh).
- `Scene.ClearNavMesh` — **0** callers. `Scene.SaveNavMeshPrefabWithFrame` — **0** callers.

Our module is the only *editor* caller of `ImportNavigationMeshPrefab` (via
`SceneNavMeshExporter`/`TerrainNavMeshGenerator`). The editor's own navmesh panel (`Import faces from prefabs`)
is native (see §3). Consequence: **there is no managed post-import step to defer async in the editor — none
exists to be optimized.**

### Editor ticking / hooks available to us

- `ScriptComponentBehavior.OnEditorTick(float dt)` (`0x06000C49`) — per-editor-frame.
- `ScriptComponentBehavior.OnEditorVariableChanged(string)` (`0x06000C48`-family) — our buttons run here.
- `ManagedScriptHolder.TickComponentsEditor(float dt)` (`0x06000925`) iterates all editor-ticking components
  and calls `OnEditorTick`. This is the editor's per-frame drive loop.
- `ScriptComponentBehavior.OnDynamicNavmeshVertexUpdate()` (`0x06000C59`) — engine callback for dynamic
  navmesh vertex changes.

## 3b. What happens *after* `ImportNavigationMeshPrefab` returns

Answer: **nothing managed.** The call is a leaf native call with no managed post-processing, no deferred
managed queue, no managed index build. Our own `WriteAndImport` reads `GetNavMeshFaceCount` right after and
that is the only post-import managed work (`facesAfterMs=0` in every run).

What the native engine does afterwards is not observable from managed code. The only native signals of
"deferred / lazy" work are the cache-update strings listed above (view-blocking-edge cache, excluded-group-id
index cache, region map). Whether those are built eagerly during `LoadNavMeshPrefab`, lazily on first use, or
incrementally on edit is **unverified**. The wall-clock evidence is consistent with "eager, and included in
`importMs`" (import scales linearly with faces and the very next managed call is instant), but that is an
inference, not a measurement.

## 4. Candidate improvements (ranked by impact / effort / risk)

> Honest framing from the data: **import is already near-linear and cheap (≈1.2 M faces/s, 1.5 M faces ≈ 1.1 s).
> The editor's slow feeling is dominated by *generation* (0.8–61 s, synchronous on the editor main thread),
> and very likely by two *unmeasured* edges: the startup prefab-list parse and the viewport/save of a huge
> imported mesh.** Ranked accordingly.

### Tier 1 — do these first (low risk, high leverage)

**1.1 Mesh-size levers (fewer faces ⇒ cheaper everywhere).**
Every measured phase scales with F: `importMs`, `writeMs`, `binBytes`, and (inferred) startup prefab parse,
scene save and viewport draw. The single biggest lever we already own is the v2 detail mesh
(**measured ≈5.8× face multiplier**: 184,248 polys → 1,069,997 triangles), plus voxel cell size
(cs 0.5 → 1.0 took 1,069,997 → 145,738 faces, ≈7×).
- Impact: high (cuts import, bin, startup, save, draw all at once). Effort: none (existing settings).
  Risk: low (mesh-quality trade-off, already documented).
- Concrete: default `NavMeshVoxelDetailMesh=false` for flat/plateau scenes; raise `NavMeshVoxelCellSize`
  and/or `NavMeshMaxErrorMeters` for edit-time work; keep full detail only for the final build.

**1.2 Instrument the unmeasured phases before optimizing them.**
The `timings:` log already proves `build/write/clear/import` are cheap, but it explicitly excludes
"everything the editor does around/after the import" (`README.md`, "Not included"). Add:
- `Utilities.GetFps()` / `GetRendererFps()` / `GetDeltaTime(0)` sampled on the `OnEditorTick` immediately
  after import, and once more a second later.
- `Utilities.StartScenePerformanceReport(folder)` + `Utilities.AddPerformanceReportToken(...)` around a run.
- a "click → next editor tick" wall-clock pair (timestamp at button, timestamp in the next `OnEditorTick`).
- Impact: high (decides Tier 2/3). Effort: low. Risk: low. All API shapes verified in §5.

### Tier 2 — editor UX (address the *perceived* freeze)

**2.1 Move generation off the editor main thread; marshal only the import back.**
v2 already parallelises tiles (`workers=12`), but the whole `RunPipeline` still runs synchronously inside
`OnEditorVariableChanged`. The scene *reads* (`SceneTerrainSampler`) and the final *import* must stay on the
main thread (native thread affinity, §3); everything between (the DotRecast build + NMG8 serialisation) is pure
managed and can run on a `Task`/worker. Use `Utilities.ConstructMainThreadJob(Delegate, params object[])`
(`0x06000D2E`) to hand the import back, and log progress from the worker.
- Impact: high (UI stays alive through the 0.8–61 s build). Effort: medium. Risk: medium
  (must not touch engine/scene objects off-thread; verify with a smoke test).

**2.2 Chunked import for responsiveness (only if full-res faces are required).**
Because import has no measurable fixed overhead, splitting one big call into K imports (per tile/region, each
with its own `navMeshGroupShift`) should cost ~the same total but returns to the editor every few hundred ms.
- Impact: medium (progress + responsiveness; total time ≈ unchanged). Effort: medium.
  Risk: medium (K new prefabs must be in the startup list — worsens the "first run can't import" problem;
  group-0 static semantics; more files).
- Note: `navMeshGroupShift` gives each chunk a group id; `GameEntity.AttachNavigationMeshFaces(groupId, …)`
  (`0x060007B1`) can then attach/enable a chunk independently (dynamic-navmesh path, see §5).

**2.3 `NavMeshImportIntoScene=false` as the default editing loop.**
Write the bin, don't import, until a playtest is actually needed. This removes import + viewport + save cost
entirely from the edit loop. Our module already supports it; the README workflow still pushes import.
- Impact: medium–high for perceived speed. Effort: none (setting). Risk: low (loses in-editor navmesh view).

### Tier 3 — Harmony (managed-only; worth it for the specific gaps)

Harmony feasibility is **confirmed in principle** (details in §6): the editor loads SubModules, `.NET 6`
hosts Harmony here (0Harmony 2.2.2 + Mono.Cecil are already loaded by other modules), and the native engine
cannot be patched.

**3.1 Skip navmesh load on scene open (highest-value patch).**
Prefix `TaleWorlds.Engine.Scene.Read` (3 overloads, `0x06000B73/74/75`) or
`SceneInitializationData..ctor` (`0x06000ABE`) to force `LoadNavMesh=false`, then import on demand.
- Impact: high if scene-open is dominated by navmesh parse (Tier 1.2 will tell us). Effort: medium.
  Risk: medium (changes engine semantics; must be opt-in, and re-import must be explicit).

**3.2 Main-thread frame budget + progress.**
Prefix `ManagedScriptHolder.TickComponentsEditor` (`0x06000925`) — or simply drive our own queue from
`OnEditorTick` — to run at most N ms of queued navmesh work per editor frame with progress in the log.
- Impact: medium. Effort: low–medium. Risk: low.

**3.3 Instrument / guard the import call itself.**
Prefix `Scene.ImportNavigationMeshPrefab` (`0x06000B9B`, managed) for timing and for a pre-flight guard
(e.g. face-count/validity sanity, or a watchdog) to avoid repeating the never-returning case.
- Impact: medium (safety, not speed). Effort: low. Risk: low.
- Note: a single synchronous native import cannot report intra-call progress, so "progress reporting" for a
  single big import is impossible without chunking (2.2).

### Evidence for the "generation dominates" conclusion

From `NavMesh_20260926_133109.log`/`NavMesh_20260929_003310.log`, same scene, same machine:

| setting | buildMs (v2 tiles) | importMs |
|---|---:|---:|
| cs 2.0 | 823 | 59 |
| cs 1.0 | 1,095–1,854 | 132–170 |
| cs 0.5 | 2,651–6,804 | 177–265 |
| cs 0.25 | 8,631 | 177 |
| cs 0.1 | **61,305** | 285 |

## 6. Harmony feasibility (managed vs native, explicitly)

**Can the editor load our SubModule and a bundled Harmony? — Yes, with one caveat to smoke-test.**

1. `TaleWorlds.MountAndBlade.Module.LoadSubModules` (`0x06002A4C`) loads each active module's SubModule DLL from
   `Path.Combine(moduleInfo.FolderPath, "bin", Common.ConfigName)` and then calls
   `MBSubModuleBase.OnSubModuleLoad()`. `TaleWorlds.Library.Common.get_ConfigName` returns
   `new DirectoryInfo(Directory.GetCurrentDirectory()).Name`, i.e. **`Win64_Shipping_wEditor` in the editor**,
   `Win64_Shipping_Client` in game — matching `build.ps1`/`csproj` deployment. `Module.Initialize` is the only
   caller that triggers the full `InitializeSubModuleBases()` → `OnSubModuleLoad()` path. **This is shared
   code, not an editor-specific branch**, so `SubModule.OnSubModuleLoad` is a valid Harmony bootstrap point.
   Caveat: I could not run the editor during this investigation to observe our SubModule's `OnSubModuleLoad`
   firing (no editor `rgl_log`/console was available); the code path makes it a high-confidence expectation,
   not a verified runtime fact.
2. **Bundling Harmony**: `SubModuleInfo.LoadFrom` (`TaleWorlds.ModuleManager`, `0x0600005C`) reads
   `<Assemblies><Assembly value="..."/></Assemblies>` into `SubModuleInfo.Assemblies`; `LoadSubModules`
   preloads every listed assembly from the module bin **without a cert check** (only the main `DLLName` is
   cert-checked via `GetIsTWCertified`). So add `0Harmony.dll` next to our DLL in
   `bin\Win64_Shipping_wEditor\` and list it under `<Assemblies>`.
3. **Runtime proof**: the process context exposed by the dnSpy bridge already had **`0Harmony 2.2.2.0`** and
   **`Mono.Cecil 0.11.4.0`** loaded (from other modules), and the engine runs on **.NET 6 CoreCLR**
   (`System.Private.CoreLib 6.0.36`; `Microsoft.NETCore.App\6.0.36` present in `bin\Win64_Shipping_wEditor`).
   Harmony 2.x is therefore proven to run in this environment.
4. **The native engine cannot be patched.** `TaleWorlds.Native.dll` has no managed metadata; the `IScene.*`
   delegate fields are native function pointers installed at startup. You can only patch the managed wrappers
   (`Scene.ImportNavigationMeshPrefab`, `ManagedScriptHolder.TickComponentsEditor`, …). Every native row in §3
   is out of reach.

**Best patch targets (managed only):**

| Goal | Target | Token |
|---|---|---|
| Skip navmesh load on scene open | `Scene.Read` overloads / `SceneInitializationData..ctor` | `0x06000B73/74/75`, `0x06000ABE` |
| Per-frame budget + progress | `ManagedScriptHolder.TickComponentsEditor` | `0x06000925` |
| Time/guard the import | `Scene.ImportNavigationMeshPrefab` | `0x06000B9B` |
| Time the bulk read | `ScriptingInterfaceOfIScene.LoadNavMeshPrefab` (postfix) | `0x0600049C` |
| Avoid O(F) drains | `Scene.GetAllNavmeshFaceRecords` | `0x06000B1F` |

## 7. Chunking / threading / progress (direct answers)

- **Per-call overhead for N small prefabs vs one big call:** measured import is linear with **no visible fixed
  cost** (27 k→20 ms, 466 k→380 ms, 1.5 M→1091 ms; throughput flat ~1.0–1.4 M faces/s). So total time for N
  chunks should be ≈ the single call. Benefit is responsiveness, not throughput; cost is N files and N entries
  in the startup prefab list.
- **Off-main-thread import:** **No** (unverified and unsafe). Native scenes have an owner thread
  (`Scene.SetOwnerThread`), native code asserts `check_is_main_thread()`, and the managed layer provides
  `Utilities.GetMainThreadId`/`ConstructMainThreadJob` precisely for marshalling. Import from a worker thread
  is unsupported.
- **Yield/split across editor ticks:** the *engine* call cannot yield once entered (the hang log proves a
  single call can block forever). Our *own* pipeline can: `OnEditorTick` runs every editor frame, so generation
  can be chunked per-tick or run on a worker (Tier 2.1) and only the final import done in one main-thread hop.

## 8. Experiment plan (what to measure next, with the user)

All of these reuse the `timings:` log plus small additions; no engine changes required for 1–5.

1. **Startup prefab-list cost (the biggest unknown).**
   With the editor closed, time "launch editor → scene usable" with
   `Modules\MyMaps\NavMeshPrefabs\` present (85 MB: 80 MB + 4.5 MB + 889 B) vs. temporarily moved aside.
   Current registry on this machine ≈ **101 prefabs** across `Native` (69), `Full Invasion 3` (14),
   `Full-Invasion-3` (13), `MapConverter` (2), `MyMaps` (3). If startup/open time drops by seconds, the
   native prefab parse is the hidden cost and Tier 3.1 is the fix.
2. **Scene-open cost with/without the large prefab**: open `mp_battle_na'ilu_L` and time to interactive, with
   the 80 MB prefab in place vs. removed. Compare against the measured 1.09 s import of 1.5 M faces.
3. **Viewport cost**: with 1.5 M faces imported, log `Utilities.GetFps()`/`GetRendererFps()`/`GetDeltaTime(0)`
   on the next `OnEditorTick` and again 1 s later; repeat after `ClearNavMesh()`, same camera. This converts
   "feels slow" into fps at 0 vs 1.5 M faces.
4. **Chunking A/B** (uses `Import Only`): compare 1 × 1.5 M prefab vs 8 × ~190 k prefabs (distinct
   `navMeshGroupShift`). Metrics: total `importMs`, max single-call latency, editor fps during the run,
   `faces after import`.
5. **Faces → wall-time curve**: for `(cellSize, detail)` ∈ `{1.0, 0.5} × {on, off}` log `F`, `binBytes`,
   `buildMs`, `writeMs`, `importMs`, next-session startup parse, and viewport fps. This is the decision table
   for Tier 1.1.
6. **Harmony smoke test**: add an editor-only Harmony bootstrap in `SubModule.OnSubModuleLoad` that (a) logs
   "harmony up", and (b) prefixes `Scene.Read` with a log + `LoadNavMesh=false`; verify it loads in the editor
   and a scene opens; then measure scene-open time before/after.
7. **Thread-safety probe** (isolated test scene only): from a worker thread call `Scene.GetNavMeshFaceCount()`
   and observe. Do **not** attempt an off-thread import until this is proven safe.

## 9. Explicit unknowns / cannot verify offline

- **Native import internals** (per-face cost, spatial index / connectivity / bounding-volume build, whether any
  of it is deferred to the next frame or first use): no PDB for `TaleWorlds.Native.dll`, Ghidra not reachable.
  All native claims are string evidence only.
- **Whether the engine defers work after import**: the managed layer defers nothing (§3b); native lazy caches
  exist by name (`auto_compute_view_blocking_edges`, `excluded_group_ids_index_cache_`, `group_id_to_region_map_`)
  but their trigger point/time is unverified.
- **Scene save / "prefab compile" cost**: no managed `Scene.Save` exists; the native save/compile path, its
  face-count scaling, and whether a tool can defer it were **not measurable** here.
- **A managed navmesh-render toggle / LOD / face limit**: none found. Only native QT options
  ("Show Auto NavMesh Regions", "Auto Nav Debug Tools"), the debug command
  `show_dynamic_navmesh_for_ranger_position [0/1]`, `debug.clear_permanent_debug_render_meshes`, and generic
  `Utilities.SetRenderMode/ToggleRender`. Whether navmesh faces honour `Scene.SetActiveVisibilityLevels` /
  upgrade-level visibility is unverified.
- **Startup prefab-parse scaling**: inferred (101 prefabs / ~85 MB in MyMaps; 1.09 s for 1.5 M faces on import)
  but not directly measured; also unverified whether the registry parses prefab *headers* or full face data per
  module at startup.
- **Harmony in the editor at runtime**: code path and runtime are confirmed; a live editor smoke test (exp. 6)
  is still required. I could not confirm which process the dnSpy bridge was attached to (its "loaded assemblies"
  list mixed client/server modules), although the decompiled `TaleWorlds.Engine.dll`/`TaleWorlds.MountAndBlade.dll`
  were opened by explicit `Win64_Shipping_wEditor` path.
- **The 1.07 M-face hang**: shown to be inside the native call, but the precise failure and whether any managed
  pre-flight validation would have caught it belongs to the (separate, in-flight) mesh-validation fix.
